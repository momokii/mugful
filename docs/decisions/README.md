# Architecture decision records

Use an ADR when a decision changes architecture, security, privacy, deployment, data contracts, or a public operational promise.

## Required ADR shape

1. **Title and status** — proposed, accepted, superseded, or rejected.
2. **Context** — the problem and constraints.
3. **Decision** — the chosen approach.
4. **Consequences** — benefits, costs, and new risks.
5. **Alternatives** — serious options considered.
6. **Follow-up** — docs, migrations, tests, or review dates.

ADRs should be short, link to the product or architecture document, and never silently contradict the current specification. When an ADR supersedes an existing decision, update `CURRENT-STATUS.md` and `ROADMAP.md` in the same change.
